1. EXECUTIVE SUMMARY
================================================================================

This project implements a complete industrial-grade Digital Twin of a KUKA
KR210 robot, driven by a real Siemens S7-1500 PLC program running in PLCSIM
Advanced, with a physics simulation in NVIDIA Isaac Sim, and a KRC (KUKA
Robot Controller) digital twin implementing online trajectory generation
with Ruckig.

The system achieves sub-0.03° joint tracking accuracy across all four
controlled axes — better than most physical industrial robots without
closed-loop encoder feedback.

Key achievement: not a toy demo, but a working industrial architecture
with safety layers, heartbeat protocol, state machine, and jerk-limited
trajectory generation.

2.2 Data Flow (Nominal Operation)

    Step 1:  PLC increments Heartbeat_Counter every 20 ms (OB30)
    Step 2:  plc_ros_bridge polls via TCP every 50 ms (20 Hz)
    Step 3:  Bridge reads CmdAng[1..4], CmdEnable, Vlcty, Heartbeat_Counter
    Step 4:  Bridge writes ROS_Ack_Counter = Heartbeat_Counter
    Step 5:  Bridge publishes /plc/cmd_ang, /plc/axis_enable
    Step 6:  krc_twin reads /plc/*, enters RUNNING state
    Step 7:  krc_twin resets Ruckig planner from actual joint positions
    Step 8:  krc_twin builds target vector from CmdAng (degrees → radians)
    Step 9:  krc_twin calls Ruckig, gets next setpoint
    Step 10: krc_twin publishes /servo_setpoints @ 60 Hz
    Step 11: physics_twin applies setpoints to Isaac articulation
    Step 12: Isaac physics computes new joint positions
    Step 13: physics_twin publishes /joint_states @ 60 Hz
    Step 14: krc_twin reads feedback, syncs Ruckig
    Step 15: plc_ros_bridge reads feedback, converts to degrees
    Step 16: Bridge writes ActAng[1..4] to PLC
    Step 17: PLC sees updated ActAng in watch table

    Total loop latency: ~150-300 ms
    (dominant factor: PLC polling at 20 Hz + TCP roundtrip)

4. PLC SIDE — SIEMENS S7-1500
================================================================================

4.1 Data Block: MAIN_KUKA_KR210_L150_L

    Note: The actual DB name in PLCSIM contains an underscore between
    "L150" and "L" — "MAIN_KUKA_KR210_L150_L". This was discovered
    during commissioning via PLCSIM's tag list dump.

    Key members used by the Digital Twin:

    ROBOT COMMANDS (PLC → ROS):
        MainRobotLeft_CmdAng         Array[1..4] of LReal
        MainRobotLeft_CmdEnable      Bool
        MainRobotLeft_Vlcty          LReal          (velocity, 0..500 %)
        MainRobotLeft_Emergency_Stop_Active   Bool

    ROBOT STATUS (read-only for ROS):
        MainRobotLeft_Motion_Active           Bool
        MainRobotLeft_Group_Fault             Bool
        MainRobotLeft_Axis1_Fault             Bool
        MainRobotLeft_Axis2_Fault             Bool
        MainRobotLeft_Axis3_Fault             Bool
        MainRobotLeft_Axis4_Fault             Bool

    ROBOT FEEDBACK (ROS → PLC):
        MainRobotLeft_ActAng         Array[1..4] of LReal
        MainRobotLeft_CmdAck         Bool

    HEARTBEAT PROTOCOL:
        Heartbeat_Counter            DInt            (incremented every 20 ms)
        Heartbeat_Timestamp          DTL             (diagnostic)
        ROS_Ack_Counter              DInt            (written by ROS)
        ROS_Ack_Timestamp            DTL             (diagnostic)
        ROS_Alive                    Bool            (TRUE only if Comm_State=0)
        Comm_State                   Int             (0=OK, 1=Late, 2=Dead, 3=BadAck)
        Comm_LostCount               DInt
        HB_Timeout_Mult              Int := 50       (cycles before Late)


4.2 Heartbeat Protocol (heartbeat.scl — OB30, 20 ms)

    Every 20 ms:
    1. Increment Heartbeat_Counter (with rollover at 2^31)
    2. Update Heartbeat_Timestamp via RD_LOC_T
    3. Compute HB_Age = Heartbeat_Counter - ROS_Ack_Counter
    4. State machine:
       State 0 (OK):    if HB_Age > HB_Timeout_Mult → State 1 (Late)
       State 1 (Late):  if HB_Age > HB_Timeout_Mult*2 → State 2 (Dead)
                        elif HB_Age <= HB_Timeout_Mult → State 0 (OK)
       State 2 (Dead):  force CmdEnable=FALSE, ROS_Alive=FALSE
                        if HB_Age <= HB_Timeout_Mult → State 0 (OK)
       State 3 (BadAck): force CmdEnable=FALSE

    Every cycle:
       ROS_Alive := (Comm_State = 0)

    Rationale (DEC-002): counter-based, not timestamp-based.
    Immune to clock drift between PLC and PC. Same mechanism used by
    PROFINET watchdog timers.

        {"cmd": "write", "tags": {"tag1": value1, ...}}
    Response:
        {"written": {"tag1": true, "tag2": true, ...}}

    List request:
        {"cmd": "list"}
    Response:
        {"tags": ["tag1", "tag2", ...]}

    - Persistent connection with newline-delimited JSON

================================================================================
6. LINUX ROS 2 BRIDGE — plc_ros_bridge.py
================================================================================

6.1 Purpose
    - Bidirectional bridge between PLCSIM (via TCP) and ROS 2.
    - Implements the ROS side of the heartbeat protocol.
    - Converts units: radians (ROS) ↔ degrees (PLC).

6.2 Topics

    Published:
        /plc/cmd_ang        sensor_msgs/JointState   (positions in degrees)
        /plc/axis_enable    std_msgs/Bool
        /plc/emergency_stop std_msgs/Bool
        /plc/velocity       std_msgs/Float64
        /plc/ros_alive      std_msgs/Bool
        /plc/cmd_ack        std_msgs/Bool

    Subscribed:
        /joint_states       sensor_msgs/JointState   (positions in radians)

6.3 Polling Loop (20 Hz)

    Every 50 ms:
    1. Read from PLCSIM (via TCP):
       - CmdAng[1..4], CmdEnable, Vlcty, Emergency_Stop_Active
       - Heartbeat_Counter, Comm_State, ROS_Alive
    2. If Heartbeat_Counter changed:
       - Write ROS_Ack_Counter = Heartbeat_Counter
    3. Publish /plc/cmd_ang (as JointState, values in degrees)
    4. Publish /plc/axis_enable, /plc/emergency_stop, /plc/velocity,
       /plc/ros_alive
    5. If /joint_states received recently:
       - Convert radians to degrees
       - Write ActAng[1..4] and CmdAck=TRUE to PLCSIM

6.4 Unit Conversion Convention

    PLC degrees  →  ROS radians:   rad = deg × π/180
    ROS radians  →  PLC degrees:   deg = rad × 180/π

    No sign flips or offsets are used in this project (JOINT_SIGN = +1,
    MAMES_DEG = 0, ISAAC_HOME_OFFSET = 0), because the URDF joint axis
    convention matched the PLC convention. If a future axis needs
    inversion, modify the conversion in this file only.


================================================================================
7. KRC DIGITAL TWIN — krc_twin.py
================================================================================

7.1 Purpose
    The heart of the project. Implements the "KRC concept":
    - Online trajectory generation with Ruckig
    - Feedback-driven control (sync from actual every cycle)
    - State machine with safe transitions
    - Jump protection against feedback discontinuities
    - Command validation before use

7.2 Topics

    Subscribed:
        /joint_states           sensor_msgs/JointState   (feedback from Isaac)
        /plc/cmd_ang            sensor_msgs/JointState   (target in degrees)
        /plc/axis_enable        std_msgs/Bool
        /plc/emergency_stop     std_msgs/Bool

    Published:
        /servo_setpoints        sensor_msgs/JointState   (target in radians)

7.3 Joint Configuration

    ROS_ORDER = ["joint_1", "joint_2", "joint_3", "joint_5", "joint_4"]
    NUM_DOF = 5

    CONTROLLED_JOINTS = ["joint_1", "joint_2", "joint_3", "joint_4"]

    Notes:
    - The order of ROS_ORDER matches the Isaac articulation DOF order.
    - joint_5 is NOT controlled; it holds its measured position.
    - Only 4 joints receive commands from the PLC.

7.4 Ruckig Parameters

    CONTROL_HZ   = 60          servo loop rate
    MAX_VEL      = 1.5  rad/s  ~86 °/s
    MAX_ACC      = 5.0  rad/s²
    MAX_JERK     = 30.0 rad/s³

    These are conservative values for a KR210-class robot, chosen for
    smooth motion without risk of saturation.

7.5 Jump Protection

    JUMP_THRESHOLD_RAD = 0.30   (~17°)

    If |measured - last| > threshold in any joint:
        Reset Ruckig's internal velocity and acceleration to zero.
        Continue from the new position.
    This prevents violent corrective motion when Isaac resets or when
    the ROS feedback drops.

7.6 State Machine

    States: IDLE, RUNNING, STOPPING

    Transitions:
        IDLE → RUNNING:       enable AND fresh_feedback AND valid_cmd
        RUNNING → STOPPING:   any fault (disable, estop, stale feedback,
                              bad command, Ruckig error)
        STOPPING → IDLE:      when Ruckig reports Finished on braking
                              trajectory

    A return to RUNNING from STOPPING requires going through IDLE
    implicitly (via the next enable+cmd cycle).

7.7 Braking Behavior

    On any fault, krc_twin switches Ruckig to Velocity interface with
    target_velocity = 0. This produces a jerk-limited deceleration
    profile.
    This matches IEC 60204-1 Stop Category 1 (controlled stop with
    power retained).

7.8 Feedback-Driven Control

    Every servo cycle:
    1. Read latest /joint_states (5 joints, radians)
    2. If fresh (within 0.5 s):
       - planner.sync_state(actual)  — inject measured position
       - planner.set_target(target)  — 5-vector in ROS_ORDER
       - planner.step()              — advance one dt
       - publish /servo_setpoints
    3. Else: enter STOPPING (braking)

    Ruckig manages internal velocity/acceleration; only position is
    overwritten each cycle.

8. ISAAC SIM PHYSICS TWIN — physics_twin.py
================================================================================

8.1 Purpose
    Minimal physics driver. Does NOT implement any control logic.
    Receives setpoints and applies them to the articulation.

8.2 Robot Configuration

    ROBOT_PATH  = "/World/Main_Robot_L_URDF/base_link"
    ROBOT_SCOPE = "/World/Main_Robot_L_URDF"
    DOF_ORDER   = ["joint_1", "joint_2", "joint_3", "joint_5", "joint_4"]
    PUBLISH_HZ  = 60

8.3 Joint Prim Paths

    joint_1: {ROBOT_SCOPE}/base_link/joint_1
    joint_2: {ROBOT_SCOPE}/link_1/joint_2
    joint_3: {ROBOT_SCOPE}/link_2/joint_3
    joint_4: {ROBOT_SCOPE}/link_4/joint_4
    joint_5: {ROBOT_SCOPE}/link_3/joint_5

8.4 Drive Gains (per joint)

    joint_1: stiffness=1,000,000  damping=100,000  max_force=50,000,000
    joint_2: stiffness=1,000,000  damping=100,000  max_force=50,000,000
    joint_3: stiffness=1,000,000  damping=100,000  max_force=50,000,000
    joint_4: stiffness=  200,000  damping= 20,000  max_force= 5,000,000
    joint_5: stiffness=  200,000  damping= 20,000  max_force= 5,000,000

8.5 Gravity Compensation

    GRAVITY_COMP = [0.0, 1200.0, 600.0, 0.0, 50.0]   (N·m)
    Order matches DOF_ORDER: [joint_1, joint_2, joint_3, joint_5, joint_4]

    Constant torque per joint, sufficient to hold the arm against gravity
    with minimal residual error. Tuned empirically.

8.6 Setpoint Handling

    On /servo_setpoints received:
        Store as dict {name: position_rad}

    On every physics frame:
        current = robot.get_joint_positions()
        For each joint i in DOF_ORDER:
            if joint_i in setpoint_dict:
                target[i] = setpoint_dict[joint_i]
            else:
                target[i] = current[i]   # hold
        robot.set_joint_position_targets(target)
        robot.set_joint_efforts(GRAVITY_COMP)

    This ensures that joints not present in the setpoint are held
    at their current position (feedback-driven hold).


================================================================================
9. HEARTBEAT PROTOCOL IN OPERATION
================================================================================

9.1 Nominal Values

    Observed in successful runs:
        Heartbeat_Counter:  37257
        ROS_Ack_Counter:    37255
        Delta:              2

    Delta of 2 means the ack is written faster than the PLC increments
    the counter. This is optimal — ROS is never the bottleneck.

9.2 Failure Modes Handled

    | Fault                          | Detection              | Reaction        |
    |--------------------------------|------------------------|-----------------|
    | ROS process stops              | HB_Age > 50            | Comm_State=1    |
    | ROS process dead > 2s          | HB_Age > 100           | Comm_State=2,   |
    |                                |                        | CmdEnable=FALSE |
    | Ack out of range / rollover    | HB_Age < 0             | Comm_State=3,   |
    |                                |                        | CmdEnable=FALSE |
    | TCP connection lost            | socket error           | bridge retries  |
    | /joint_states stale > 0.5s     | no callback            | bridge: no write|
    |                                |                        | krc_twin: brake |
    | Emergency stop                 | EStop flag = TRUE      | krc_twin brakes |
    | Ruckig error (5 consecutive)   | error counter          | krc_twin brakes |

12. ENGINEERING DECISIONS (SUMMARY)
================================================================================

    DEC-001  PLC as heartbeat master, ROS as slave
             Mirrors PROFINET/EtherCAT practice.

    DEC-002  Counter-based handshake, not timestamp-based
             Immune to clock drift. Same as PROFINET watchdog.

    DEC-003  Separate Python processes: 3.10 (ROS) + 3.11 (Isaac)
             ROS 2 as the inter-process boundary.

    DEC-004  Ruckig for online trajectory generation
             Time-optimal, jerk-limited, production-proven.

    DEC-005  Jump protection with 0.3 rad threshold
             Prevents violent corrections to noisy feedback.

    DEC-006  Velocity-interface braking (Stop Category 1)
             Matches IEC 60204-1 controlled stop.

    DEC-007  Feedback injection every servo cycle
             Matches KRC interpolator behavior.

    DEC-008  pass_to_input() after every Ruckig step
             Required for stateful OTG correctness.

    DEC-009  Three-state machine: IDLE / RUNNING / STOPPING
             IEC 61131-3 SFC semantics without overhead.

    DEC-010  Command validation before use
             Last line of defense against bad PLC data.

    DEC-011  No fake zeros on missing feedback
             Fault is visible at the PLC (Ack stops).

    DEC-012  TCP/JSON transport (not OPC UA in this version)
             OPC UA is deferred — TCP was already in place.

    DEC-013  Transport isolated from control logic
             Enables future migration to PubSub / PROFINET.

    DEC-014  Rate-limited logging via log_every()
             Bounds log volume under persistent faults.

    DEC-015  Reconnect loop with force-disable on failure
             Automatic recovery with safe state.

    DEC-016  __slots__ on hot-path objects
             Micro-optimization for high-frequency callbacks.

    DEC-017  Pre-allocated buffers in servo loop
             Removes GC pressure from the 60 Hz control loop.

    DEC-018  ROS 2 QoS left at defaults
             RELIABLE, VOLATILE, depth=10.

    DEC-019  Isaac Sim as physics twin only
             Keeps KRC twin testable in isolation.

    DEC-020  No PubSub in this version
             Deferred to a future version with TIA V16+.

        MainRobotLeft_CmdEnable := TRUE

    Expected sequence within 200 ms:
        1. plc_ros_bridge publishes /plc/axis_enable = true
        2. krc_twin enters RUNNING state (logs "→ RUNNING")
        3. /servo_setpoints starts publishing at 60 Hz
        4. Isaac robot moves
        5. ActAng[1..4] in TIA updates, tracking CmdAng[1..4]

13.5 Shutdown

    In TIA Portal:
        MainRobotLeft_CmdEnable := FALSE
    Wait for robot to brake to stop.
    Ctrl+C in Linux windows in reverse order.
    Close Isaac Sim script.
    Ctrl+C in Windows TCP server.


================================================================================
14. TROUBLESHOOTING GUIDE
================================================================================

14.1 CmdEnable stays FALSE despite writing TRUE

    Root cause: Heartbeat protocol in OB30 detects ROS as dead.
    Diagnostic: read Comm_State and ROS_Alive from PLCSIM.
    Fix: ensure plc_ros_bridge.py is running and writing ROS_Ack_Counter.

14.2 "DoesNotExist" errors from PLCSIM

    Root cause: wrong tag name.
    The actual DB name is "MAIN_KUKA_KR210_L150_L" (with underscore).
    Verify by listing all tags from PLCSIM: instance.TagInfos.

14.3 TCP connection refused

    Root cause: plc_server_win.py not running, or firewall blocking.
    Diagnostic: python3 -c "import socket; ..." connect test.
    Fix: start server, allow port 5000 in Windows firewall.

14.4 /servo_setpoints shows 0 Hz

    Root cause: krc_twin in IDLE state.
    Check: /plc/axis_enable must be true, /joint_states must be fresh.

14.5 Robot does not move despite /servo_setpoints publishing

    Root cause: Isaac Sim in Edit mode (not Play), or wrong joint names.
    Check: DOF_ORDER must match Isaac articulation DOF names exactly.

14.6 Oscillation / vibration

    Root cause: drive stiffness too low, or jump protection firing.
    Fix: increase joint stiffness in physics_twin.py, or increase
    JUMP_THRESHOLD_RAD in krc_twin.py.

14.7 Tracking error > 0.5°

    Root cause: gravity load on joint_2, or saturation.
    Fix: increase GRAVITY_COMP[1], or increase joint_2 stiffness.

15. KNOWN LIMITATIONS
================================================================================

    L-01  TCP/JSON is used instead of OPC UA.
          OPC UA would be more industrial, but TCP was already in place
          from a previous test bridge and works reliably.

    L-02  Joint_5 is not controlled (only 4 axes from PLC).
          This matches the current PLC DB structure (CmdAng[1..4]).
          Adding joint_5 would require extending the PLC DB.

    L-03  Isaac physics runs at 25-60 Hz (target 60).
          Physics rate may drop under load. Feedback rate follows.

    L-04  Bridge polls at 20 Hz.
          This creates a 50 ms latency floor for command propagation.
          Sufficient for supervisory control.

    L-05  Linux process is not real-time (no PREEMPT_RT).
          Timing jitter is bounded but not deterministic.

    L-06  No Cartesian motion or inverse kinematics.
          Only joint-space commands are supported.

    L-07  Single trajectory at a time.
          No queueing, no blending between multiple waypoints.

    L-08  No authentication on TCP protocol.
          Expected to run on isolated industrial network.
